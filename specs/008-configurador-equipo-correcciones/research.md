# Research: Correcciones del Configurador de Equipo y la Pokédex

Every item below was resolved by reading the current implementation (built by `004-pokedex-team-builder` through `007-configurador-equipo-mejoras`) against the bug reports in `spec.md`, plus live-checking the external data sources this app already calls (PokeAPI, `github.com/PokeAPI/sprites`). No `[NEEDS CLARIFICATION]` markers remained in the spec, so this file records root-cause analysis and design decisions rather than open questions.

## Decision 1 — Team-slots column doesn't fill free space (User Story 2, FR-003)

**Root cause**: `TeamBuilderTwoPaneLayout` (`lib/presentation/team_builder/widgets/team_builder_two_pane_layout.dart`) wraps the slots column in `SizedBox(width: _slotsColumnWidth)` with `_slotsColumnWidth = 320` (a hardcoded constant), and its `TeamSlotRow` renders a `GridView.count(shrinkWrap: true, physics: NeverScrollableScrollPhysics)` — a grid explicitly sized to its own content, never to its container. Both dimensions are therefore fixed/content-sized regardless of how much room the window actually has, which is exactly what the report describes as "no ocupa todo el espacio libre".

**Decision**: Keep the two-pane split (left slots / right Pokédex, independent scroll — 007's User Story 2 is not being revisited), but:
- Replace the fixed-width `SizedBox` with a `ConstrainedBox`/flexible width driven by `LayoutBuilder` (a minimum comfortable width for the 3-wide slot grid, growing with the available window width up to a sensible cap so the Pokédex column always keeps the majority of the space — the same intent `_slotsColumnWidth` already encoded, just no longer a single fixed number).
- Replace the shrink-wrapped `GridView.count` with an `Expanded`/`GridView` combination so the slots grid's tiles grow to fill the column's available height instead of leaving dead space below a 2-row grid on a tall window.

**Alternatives considered**: A `Flexible`/`Expanded` split of the whole `Row` (e.g. `flex: 1` / `flex: 3`) was considered instead of a width cap, but rejected — an unconstrained-growth slots column on an ultra-wide monitor would stretch 6 small square tiles across most of the screen, which is worse than the current problem. A bounded-growth width (grow to fill, cap at a multiple of the tile size) preserves "fill the free space" without that regression.

## Decision 2 — Pokédex doesn't finish loading (User Story 1, FR-001/FR-002)

**Root cause**: The Pokédex *index* (id + number for every species) is always fetched in full up front (`PokeApiPokedexRepository.fetchPokedexIndex`) — so the grid's `childCount` already reflects every entry from the start; what's incremental is only each tile's *detail* (sprite/name/types), resolved 20 at a time by `TeamBuilderCubit._resolveNextBatch`, triggered by a `NotificationListener<ScrollNotification>` that calls `loadMoreIfNeeded()` only when a scroll notification's metrics land within 400px of the bottom (`team_builder_two_pane_layout.dart`, `team_builder_page.dart`). This is correct for a continuous drag-scroll, but it depends entirely on the *number and shape* of scroll notifications the user's gesture happens to produce — a fast fling, a trackpad/mouse-wheel burst, or simply never scrolling far enough in one continuous motion can leave large stretches of the dex permanently unresolved (visually indistinguishable placeholder tiles, `_PokedexPlaceholderTile`), which reads as "faltan Pokémon" even though every species' index slot is technically present.

**Decision**: Trigger `loadMoreIfNeeded()` from proximity to the *rendered* end of the grid instead of only from scroll-position deltas — `PokedexGridSliver`'s `SliverChildBuilderDelegate.builder` callback already fires for every tile Flutter actually builds (including as new tiles enter the cache extent while scrolling, and for whichever tiles are already within the cache extent on first paint, before any scroll event exists at all); call `onLoadMore()` whenever the tile index being built is within a fixed lookahead (`_loadMoreLookahead = 10`) of the end of `indexEntries`. This fires the moment a near-the-end placeholder is *about to be shown at all* — whether that happens because the user scrolled there or because the initial viewport/cache-extent already reaches it on a short list or a large window — rather than depending on a scroll notification's pixel-distance math ever crossing the 400px threshold. `loadMoreIfNeeded()` itself is unchanged (`TeamBuilderCubit`'s existing `isLoadingMore` in-flight guard and "no unresolved ids left" no-op both already make repeated calls from the same or nearby tiles harmless and idempotent — no risk of resolving more than one bounded `_batchSize = 20` batch per outstanding gap). The existing `NotificationListener<ScrollNotification>` 400px trigger is kept alongside this, not replaced — the two are redundant by design (both funnel into the same idempotent `loadMoreIfNeeded()`), which is strictly safer than picking one.

**Alternatives considered**: Making `TeamBuilderCubit._resolveNextBatch` self-chain across multiple 20-entry batches within a single call (resolve batch, check for more unresolved, resolve again, ...) was considered first — rejected: with no notion of "the visible viewport" available to the Cubit, the only bound available to such a loop is "the whole filtered index", which on an unfiltered ~900-species National Dex would silently resolve far more than one batch per trigger and defeat the entire reason `007-configurador-equipo-mejoras` introduced batching (SC-003's "first ~20 entries in under 1s", and every batch after it staying cheap). Anchoring the trigger to what the grid is actually about to render, instead, keeps every single trigger bounded to exactly one `_batchSize` batch, requires no `TeamBuilderCubit`/state-shape change at all, and is a smaller, lower-risk diff confined to `pokedex_pane_slivers.dart`.

## Decision 3 — Type icons aren't "official" (User Story 3, FR-004)

**Root cause**: `typeIconUrl` (`lib/presentation/team_builder/widgets/type_icon_resolution.dart`) deliberately varies the icon *per game's generation*, sourcing each generation's own in-game HUD-style type icon from `github.com/PokeAPI/sprites/sprites/types/<generation>/<game-id>/<type-numeric-id>.png` (verified live: both a Generation III path and a Generation VII path resolve with HTTP 200 but render visibly different pixel-art styles). That was a deliberate design from `006-selector-pokedex-fixes-2` (era-accurate icons), but it means the same type (e.g. Fire) renders as a different-looking icon depending on which game is open — never the single, consistent icon most players recognize as "the" official type icon (the modern rounded-badge set used across current official Pokémon apps/sites), which is what the report is asking for.

**Decision**: Resolve every type icon from one fixed, generation-independent source instead of branching on `game.generation.id` — the same repository's newest available icon set (Generation IX / `scarlet-violet` folder), which is the closest match to the "official" icon most users expect, used uniformly for every game the app supports. `iconForPokemonType`'s bundled Material-icon map remains as the network-failure fallback, unchanged.

**Addendum — the network icon isn't even reaching the two places the report is actually about**: `typeIconUrl` today has exactly one caller, `_TypeIcon` (private to `pokedex_type_filter.dart`, the type *filter chips*). `TeamSlot` (`team_slot.dart:121`) and `PokemonCustomizationCard` (`pokemon_customization_card.dart:140`) — the two places a user actually looks at a Pokémon's type once it's on the team, which is what the report's screenshots/flow are about — call `Icon(iconForPokemonType(type.id), ...)` directly, i.e. only the bundled generic Material-icon fallback (a plain circle, flame, water-drop, ...), never `typeIconUrl`'s real Pokémon-art icon at all. So the report is really two stacked defects: (a) the one place that *does* fetch a real icon varies it by generation (fixed above), and (b) the two places the report is actually screenshotting never fetch a real icon in the first place.

**Decision (continued)**: extract `_TypeIcon` out of `pokedex_type_filter.dart` into a shared, public widget — `PokemonTypeIcon` in `type_icon_resolution.dart` itself (same file `typeIconUrl` already lives in, keeping the "how to render a type" concern in one place) — taking just `PokemonType type` (no `game`, per the generation-independence decision above) and rendering the network icon with the same Material-icon-on-`null`/on-network-error fallback `_TypeIcon` already implements. `TeamSlot`, `PokemonCustomizationCard`, and `PokedexTypeFilter` all render type icons through this one widget instead of each choosing (or in two of the three cases, failing to choose) independently.

**Alternatives considered**: Keeping per-generation icons but only for the Pokédex historically accurate to that generation was considered (i.e., only change the games that look most "wrong") — rejected as unnecessary complexity (Principle I): a single fixed icon set is simpler, satisfies the report as stated ("los tipos no están usando los iconos oficiales"), and removes an entire branch (`_generationsWithTypeIcons`/`_oldestIconGeneration`) rather than growing it. Leaving three independent call sites to each separately decide between the network icon and the Material fallback was also considered and rejected — a shared `PokemonTypeIcon` widget is the smaller change and guarantees the slot, the card, and the filter chips can never drift apart on this again.

## Decision 4 — Customization card doesn't reflect gender/shiny/mega/form changes (User Stories 4, 6, 7, FR-005, FR-008–FR-010)

**Root cause**: `TeamBuilderPage._openCustomizationCard` opens `PokemonCustomizationCard` via `showModalBottomSheet`'s `builder`, passing `entry`/`rosterEntry` captured once from `state.slots[slotIndex]` **before** the sheet opens. `PokemonCustomizationCard` is a plain `StatelessWidget` with no `BlocBuilder`/`BlocConsumer` inside it — so once mounted, its `rosterEntry` field never changes for the lifetime of the sheet, no matter how many times `onChanged` fires and updates `TeamBuilderCubit`'s state. Every control's `onChanged` computes its next value as `rosterEntry.copyWith(<the one field this control owns>)` off that same frozen field (e.g. `pokemon_customization_card.dart:152,209,260-280`) — so a second control tapped in the same session composes off the *original* opening-time snapshot, not the value the first tap just persisted, silently reverting every other field to what it was when the sheet opened. Concretely:
- Gender (User Story 4): tapping a segment *does* persist correctly the first time, but the segmented control's own `selected` set is also computed from the same frozen field, so it never visually updates — reads as "the toggle doesn't work" even on its very first tap, because the highlighted segment never seems to move; a second tap (before closing/reopening) discards the first tap's gender choice entirely.
- Shiny + Mega (User Story 6): tapping Shiny persists `isShiny: true` correctly (`rosterEntry.copyWith(isShiny: true)` off the frozen snapshot, where nothing else has changed yet). Tapping Mega next calls `rosterEntry.copyWith(megaActive: true, gigamaxActive: false)` — but `rosterEntry` is still the *original* frozen snapshot (`isShiny: false`), so the persisted result becomes `{isShiny: false, megaActive: true}`: the shiny flag set moments earlier is silently wiped out, which is exactly "vuelve a su forma base [no shiny] no a la forma shiny de la mega". The sprite/type resolution logic itself (`slot_sprite_resolution.dart`) already correctly combines a selected form with shiny/gender when both are present in the same `RosterEntry` — this is a pure UI/data-flow bug, not a resolution-logic bug.
- Form change (User Story 7): the same mechanism — `_applyFormChange` computes off the frozen `rosterEntry`, and even when it succeeds in persisting the new `formVarietyId`, the modal's own `entry`/`rosterEntry` fields (sprite, type chips, and — once added — base stats) never re-render with the new form, because nothing tells the `StatelessWidget` to rebuild. Only the *team slot* behind the sheet (which is driven by `BlocBuilder<TeamBuilderCubit, TeamBuilderState>` at the page level) ends up correct once the sheet closes — matching the report's "solo en el slot, no en la card".

**Decision**: Make the sheet's content reactive to `TeamBuilderCubit`'s live state instead of a frozen constructor snapshot. Concretely, wrap the `PokemonCustomizationCard` passed to `showModalBottomSheet`'s `builder` in a `BlocBuilder<TeamBuilderCubit, TeamBuilderState>` that re-reads `state.slots[slotIndex]` on every emission and rebuilds the card with the fresh `entry`/`rosterEntry`; `onChanged` keeps calling `cubit.updateRosterEntry(slotIndex, updated)` exactly as today, but `updated` is now always derived from the freshest persisted `RosterEntry`, so consecutive taps compose instead of clobbering each other. Documented as a contract in `contracts/pokemon_customization_card_reactivity.md` since it changes an interaction guarantee (every field the card exposes is expected to survive every other field's change within the same open session) that the previous implementation silently violated.

**Alternatives considered**: Converting `PokemonCustomizationCard` itself into a `StatefulWidget` that holds its own local `RosterEntry` copy, updated optimistically on every `onChanged` and only written through to the Cubit on close, was considered — rejected: it introduces a second source of truth for the same data the Cubit already owns (risk of the two diverging, e.g. if `removePokemon`/a concurrent roster change happens while the sheet is open), and Constitution Principle I favors the smaller fix of making the existing single source of truth (the Cubit) actually drive the view, over adding local state that has to be kept in sync with it.

## Decision 5 — "Sin género" (none) applied too broadly (User Story 5, FR-006/FR-007)

**Root cause, part A (perceived)**: `PokemonCustomizationCard._showsGender` (`entry.genderRate > 0 && entry.genderRate < 8`) already matches the intended rule — the gender section (and therefore any non-"sin género" choice) is only offered for a species whose `pokemon-species.gender_rate` is 1–7 (both male and female legitimately occur); a genderless species (`-1`) correctly gets no gender section at all. Because of Decision 4's staleness bug, however, gender selection appears broken across the board, which reads to a user testing many species in sequence as "gender basically never works, so it looks like nothing has a real gender" — this half of the report is resolved by Decision 4, not by a separate data-model change.

**Root cause, part B (real gap)**: a species with a genuinely **single fixed** gender — `gender_rate == 0` (always male, e.g. most of the Nidoran-M line's relatives) or `gender_rate == 8` (always female, e.g. the Nidoran-F line) — is currently treated the same as a fully-ungendered species by `_showsGender`: the whole gender section is hidden, and `RosterEntry.gender` is left `null` forever (never auto-assigned), so `slot_sprite_resolution.dart`'s `_isFemale` check (`rosterEntry.gender == Gender.female`) always evaluates `false` for such a species — silently treating an always-female species as if it were male for sprite-resolution purposes, and giving the user no way to see that this species does have a fixed, known gender. This is the case the report is pointing at with "no todos los pokémon tienen macho y hembra" — the fix must not just leave a fixed-gender species in limbo alongside true genderless species.

**Decision**: `AddPokemonToTeam` auto-applies the species' one legitimate gender when it is fixed — `Gender.male` for `genderRate == 0`, `Gender.female` for `genderRate == 8` — at the moment the Pokémon is added to the team, the same way it already auto-applies `teraType` for Escarlata/Púrpura (`add_pokemon_to_team.dart:45`). The customization card's gender section continues to show only for the 1–7 (both-genders) case; a fixed-gender species simply carries its correct, already-resolved gender with no picker to change it (there is nothing to pick), and a genuinely genderless species (`-1`) keeps `RosterEntry.gender == null` and is presented as "sin género" — restoring the intended three-way split (both genders with a picker / one fixed gender with no picker / no gender at all) instead of today's effective two-way split (pickable / hidden-and-defaulted-to-male).

**Alternatives considered**: Showing a *disabled* gender section with the one fixed gender pre-selected (instead of no section at all) was considered — rejected as unnecessary UI surface for a choice that never has more than one legitimate value; auto-applying the value and simply not showing a picker for it keeps the card's "Género" section meaning "there is a choice to make here" (Principle I).

## Decision 6 — Base stats missing from the customization card (User Story 8, FR-011/FR-012)

**Root cause**: `PokedexEntry` and `SelectableForm` do not carry base stats at all today — `PokeApiPokedexRepository._buildEntry`/`_classifyOtherVarieties` already fetch each variety's full `pokemon` JSON body (for sprites/types), but never read its `stats` array, and no domain value object exists to hold six base-stat values. This is a genuine gap, not a defect in existing logic — no code path currently attempts to show base stats anywhere.

**Decision**: Add a small, framework-free `PokemonStats` value object (`hp`, `attack`, `defense`, `specialAttack`, `specialDefense`, `speed` — the standard six, per the Assumptions in `spec.md`) mirroring `PokemonType`'s shape. `PokeApiPokedexRepository` reads `pokemon.stats` (`stat.name` → the matching field, `base_stat` → its value) from the same already-fetched `pokemonBody` for the principal variety, and from the same already-fetched `varietyPokemonBody` for every `SelectableForm` (including Mega/Gigamax) — no additional HTTP request either way, matching the pattern every other per-form field (`typePrimary`, sprites) already follows. `PokemonCustomizationCard` gains a "Base Stats" section that reads `resolveSlotStats(entry, rosterEntry)` (a new function in `slot_sprite_resolution.dart`, following the same `_matchedForm` precedence `resolveSlotTypes` already uses) so the shown stats always match the currently selected form, consistent with Decision 4's reactivity fix.

**Alternatives considered**: Fetching stats lazily only when the customization card opens (a dedicated on-demand request) was considered — rejected: the per-form `pokemon` body is already fully fetched during `fetchPokedexDetails`/`_classifyOtherVarieties` for sprites/types, so reading one more array off the same JSON is free, while a separate on-demand fetch would add a new loading state and a new failure mode for no benefit (Principle I).
