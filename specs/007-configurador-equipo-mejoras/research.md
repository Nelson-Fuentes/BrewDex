# Phase 0 Research: Mejoras al Configurador de Equipo Pokémon

No `NEEDS CLARIFICATION` markers remain in the Technical Context — every unknown below is a **design decision**, not a missing requirement (the requirements themselves were resolved in `/speckit-clarify`). Each entry follows Decision / Rationale / Alternatives considered.

## Decision 1 — Game switch becomes an unconditional reset, and the reconciliation machinery is deleted

**Decision**: `GameSelectionCubit.selectGame` persists the new selection and writes an **empty** roster every time it's called (including re-selecting the already-active game — Clarifications Q1/Q2). `requestGameSwitch`, `cancelGameSwitch`, `confirmGameSwitch`, `GameSelectionState.pendingGameSwitch`, `GameSelectionState.rosterRemovalNotice`, both `AlertDialog`s in `game_selection_page.dart`, and the `SwitchGame`/`TeamBuildingSession` reconciliation use case are deleted outright — none of them can be reached once no game selection ever partially preserves a roster.

**Rationale**: The current two-step "request → confirm, then reconcile and maybe show a removal notice" flow exists solely to support *partially* carrying a roster across a game switch. The clarified behavior ("every selection is a new team") removes that case entirely, so the state machine built to support it becomes unreachable dead code — keeping it would violate Constitution Principle I (Simplicity & YAGNI). `TeamRosterStore.writeRoster(const [])` already exists and is exactly what's needed.

**Alternatives considered**: Keep `confirmGameSwitch`/dialogs wired but skip *showing* the dialog (auto-confirm) — rejected: it leaves an now-untestable, purely-decorative state machine in place for no behavior it still needs to support, and it's the literal bug the user reported ("no responde siempre" — the dialog/confirmation path is unreliable), so removing the path is also the actual bug fix, not a workaround.

## Decision 2 — Two-pane web layout is a body swap gated by the existing `Breakpoints`, not a new breakpoint

**Decision**: `TeamBuilderPage` renders its existing single-column `CustomScrollView` body unchanged for `ScreenSize.compact`/`.medium`, and a new `TeamBuilderTwoPaneLayout` (`Row` with a fixed-width team-slots column on the left and an `Expanded` Pokédex column on the right, each with its own `Scrollable`/`CustomScrollView`) for `ScreenSize.expanded`. The switch reads `Breakpoints.resolve(MediaQuery.sizeOf(context).width)` (the same helper `ResponsiveLayout` already uses), not a bespoke `kIsWeb`/platform check — a maximized desktop *app* window also gets the two-pane layout, and a narrow browser tab does not, matching how every other adaptive surface in this app already decides.

**Rationale**: The app already has exactly one designed breakpoint system (`lib/shared/design_system/layout/breakpoints.dart`, `compact` < 600, `medium` < 840, `expanded` ≥ 840) used by `AdaptiveScaffold`/`ResponsiveLayout` everywhere else. Introducing a second, feature-specific width threshold (e.g. the spec's placeholder "1024px" assumption) would fragment the app's responsive behavior and contradict Constitution Principle I. `AdaptiveScaffold`'s `web` variant already centers content at a 1000px max width, which comfortably fits a two-pane layout without further change.

**Alternatives considered**: A platform check (`kIsWeb`) — rejected per FR-003's own framing ("versión web (escritorio)"), which the existing codebase already expresses as `ScreenSize.expanded`, not as a build target; a resizable/draggable split — out of scope, no requirement asked for it.

## Decision 3 — Split the Pokédex port into a cheap index fetch and a batchable detail fetch; "search the API directly" resolves against the index, not a live per-keystroke call

**Decision**: `PokedexRepository.fetchPokedex(...)` (which today resolves *every* species' full detail — species body, principal-variety `pokemon` body, both types, every other variety's body, cosmetic variants — before returning anything) is replaced by:
- `fetchPokedexIndex({game, view, languageCode}) → List<PokedexIndexEntry>`: the ordered `{pokemonId, pokedexNumber, sourceTag}` list already available directly from each resolved Pokédex resource's `pokemon_entries` (no per-species HTTP calls — this is the cheap part that already exists inside today's `fetchPokedex`, just returned before the expensive per-species enrichment loop).
- `fetchPokedexDetails({game, pokemonIds, languageCode}) → List<PokedexEntry>`: runs today's existing per-species enrichment (unchanged logic, just callable for an arbitrary subset of ids instead of always "all of them").

`TeamBuilderCubit` fetches the index once per view, then calls `fetchPokedexDetails` for the first ~20 ids to display immediately, and again for the next ~20 as the user nears the end of the loaded list (infinite scroll). Typing in the search box filters the already-fetched **index** (all ~900+ ids/slugs, an in-memory string match — this is genuinely instant, no network round trip) and then calls `fetchPokedexDetails` only for the ids that matched and aren't resolved yet, so a search hit outside the currently-loaded window still renders fully.

**Rationale**: Profiling the current code path shows the slowness is not "one big list request" — it's N+ sequential/parallel HTTP round trips *per species* (species body, principal variety body, generation, both type bodies, every other-variety body) all awaited via a single `Future.wait` before `fetchPokedex` returns anything at all. Splitting the cheap ordering/index step from the expensive per-species enrichment step is what actually makes "~20 first, rest incremental" possible, and reusing the *same* enrichment code for a search hit is what satisfies FR-008 without needing a search endpoint PokeAPI doesn't have. PokeAPI does not expose partial/fuzzy name search on any resource — `pokemon-species/{id or exact name}` is the only per-species lookup, and there is no `?q=` style endpoint on `pokedex` or `pokemon-species` collections. "Consulta directa a la API" (FR-008) is therefore best read as *not being limited to whatever the app happened to already batch-load* — satisfied by matching against the always-complete index and then resolving detail on demand — rather than literally issuing a live search HTTP request PokeAPI cannot answer.

**Alternatives considered**: Keep `fetchPokedex` eager but cap it at 20 for display while a background isolate keeps resolving the rest — rejected: still pays the full network cost up front (would not fix SC-004, "no perceptible esperas" scrolling a full dex, since the background fetch competes for bandwidth with the visible scroll's own batches, and doesn't help search-outside-window at all without the same index/detail split anyway); calling PokeAPI's `pokemon?limit=20&offset=N` collection endpoint directly for pagination — rejected: that endpoint isn't Pokédex-scoped (it can't honor `PokedexView`'s regional/national/DLC selection or `pokedexNumber` ordering used throughout this codebase), whereas the existing per-dex `pokemon_entries` list already carries exactly the right scoped ordering for free.

## Decision 4 — Fix shiny/gender sprite resolution by resolving those fields at the *form* level, and reuse the same fix for slot-level types

**Decision**: `SelectableForm` gains `typePrimary`, `typeSecondary`, `homeSpriteFemaleUrl`, `homeSpriteShinyFemaleUrl` (mirroring the fields `PokedexEntry` already carries for the *principal* variety) populated in `PokeApiPokedexRepository._classifyOtherVarieties` from the **same** `varietyPokemonBody` already fetched there (no new HTTP calls — the `sprites`/`types` the current code discards for a non-principal variety already exist in that response). `slot_sprite_resolution.dart`'s `resolveSlotSpriteUrl`/`hasShinySprite` are amended to read the *matched form's* female/shiny-female fields instead of always falling through to `entry.homeSpriteFemaleUrl`/`entry.homeSpriteShinyFemaleUrl` (the bug: today's code does exactly that fallthrough for a selected `formVarietyId`/Mega/Gigamax, which is why gender never varies by form and — combined with an always-null `SelectableForm.homeSpriteShinyFemaleUrl` today — is also why shiny-plus-gender is wrong for a form). A new `resolveSlotTypes(entry, rosterEntry)` helper in the same file returns the matched form's `typePrimary`/`typeSecondary` when one is active, else the entry's own — used by both `TeamSlot` (FR-015) and `PokemonCustomizationCard` (FR-017).

**Rationale**: The bug report ("shiny/gender shows the *default* form's sprite") is exactly explained by the current code's fallthrough once a form/Mega/Gigamax `RosterEntry` field is set — the female/shiny-female branch only ever reads `entry.*`, never the matched `SelectableForm`. Types have the identical shape of bug (`TeamSlot`/`PokemonCustomizationCard` would otherwise have to read `entry.typePrimary` regardless of the selected form), so both are fixed by the same data-completeness change plus the same style of resolver function already established by this file.

**Alternatives considered**: Compute female/shiny sprites and type on the fly by re-fetching the selected variety's `pokemon` resource when a form is chosen — rejected: `PokeApiPokedexRepository` already fetches that exact resource once per variety while building `selectableForms`/`megaForm`/`gigamaxForm`; re-fetching it again at selection time would be a redundant network call for data already in hand.

## Decision 5 — Tera Type is a plain field on `RosterEntry`, defaulted once at add-time, never recomputed afterward

**Decision**: `RosterEntry` gains `PokemonType? teraType`. `AddPokemonToTeam` sets it to the added entry's `typePrimary` (the principal variety's, since form selection happens as a follow-up step in the existing add flow — see `TeamBuilderPage._addPokemon`) whenever the target game is Escarlata/Púrpura (`game.id == 'scarlet-violet'`); `null`/unused for every other game. A new `TeraTypePicker` widget on `PokemonCustomizationCard` (shown only for that game) lets the user overwrite it to any of the 18 known types via `TeamBuilderCubit.updateRosterEntry`, same as every other customization field. Once set (at add-time or by the user), a later form change never recomputes `teraType` — there is no second, distinct "still at its default" state to preserve, matching Clarifications Q3's literal answer and avoiding a second hidden boolean flag on `RosterEntry` purely to distinguish "default-and-untouched" from "user re-picked the same value".

**Rationale**: Matches the clarified answer exactly (default = primary type at add time, user-editable afterward) with the smallest domain footprint — one nullable field, no new entity, no per-game branching inside the domain layer itself (the game-id check lives in the application-layer `AddPokemonToTeam` use case and the presentation-layer picker's visibility condition, consistent with how Mega/Gigamax availability is already gated by data rather than by the domain type itself).

**Alternatives considered**: Compute Tera Type on the fly (never persisted) from whatever the entry's current primary type is — rejected: it cannot represent "user explicitly picked something different from the primary type," which is exactly what FR-016b asks for; tracking a separate `teraTypeManuallySet` flag to recompute the default across form changes until the user's first manual edit — rejected as unneeded complexity for a corner case (form changed before Tera Type ever touched) the user can already correct in one tap via the always-visible picker (Principle I).

## Decision 6 — Pokébola background is a small reusable presentation widget, not an image asset

**Decision**: A new `PokeballBackground` `StatelessWidget` (CustomPainter-drawn: white/light top half, colored bottom half, a center band, a center button circle) takes a single `PokeballTone` (`neutral` | `accent`) and renders behind the sprite in `PokedexEntryCard`, `TeamSlot`, and `PokemonCustomizationCard`. `accent` maps to `colorScheme.primary`/`primaryContainer` (the same purple already used for "in team"/selected highlighting elsewhere in this codebase — `PokedexEntryCard.inTeam` already uses `primaryContainer`); `neutral` maps to `colorScheme.surfaceContainerHigh`/`outlineVariant` (today's default, un-highlighted look). Which tone applies is a presentation-only decision made by each caller: `PokedexEntryCard` → `accent` iff `inTeam`; `TeamSlot` → `accent` iff that slot is the active/open one; `PokemonCustomizationCard` → always `accent` (matches the reference mockup).

**Rationale**: A vector-drawn widget needs no asset file, trivially recolors via the existing `ColorScheme` (so it's automatically theme/dark-mode-correct, unlike a bitmap), and keeps this feature's UI additions inside the pure-Flutter presentation layer alongside `AdaptiveScaffold`/`ResponsiveLayout` — no new asset pipeline, no new dependency.

**Alternatives considered**: A bundled SVG/PNG pokéball asset — rejected: would need two (or more) pre-colored variants to satisfy the two required tones, doesn't recolor for theme changes without extra tinting logic, and adds an asset-loading dependency this app doesn't otherwise have for iconography (`Icons.*` is used throughout instead).
