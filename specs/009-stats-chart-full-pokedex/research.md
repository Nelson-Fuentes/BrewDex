# Research: Gráfico de Barras para Estadísticas y Pokédex Completa

## Decision 1 — Bar chart implementation: plain layout widgets, no charting dependency

**Context**: `pokemon_customization_card.dart`'s `_StatsTable` (added in `008-configurador-equipo-correcciones`) currently renders each of the six base stats as a `Row(Text(label), Text(value))` — a plain label/value list, not a proportional visual. The user-supplied reference design shows other UI elements (team cards, grid) but the actual bar-chart look for stats is described in the request text, not the image — the image establishes overall visual language (rounded cards, soft colors), not a specific stats-chart mockup.

**Decision**: Replace `_StatsTable` with a small `_StatsBarChart` widget built from `Column`/`Row`/`Expanded`/`Stack`/`FractionallySizedBox` — a fixed-width label, a track (`DecoratedBox` with the theme's `surfaceContainerHighest` or similar), and a filled bar (`FractionallySizedBox(widthFactor: value / _maxScale)` in the theme's primary/accent color) layered inside it, with the numeric value shown at the end of the row. No new package.

**Rationale**: Every other custom visual already in `pokemon_customization_card.dart`/`team_builder` (`PokeballBackground`, `_FormTile`, `_VariantTile`, the type `Chip`s) is built the same way — plain Flutter primitives, no charting/graphing library — and a horizontal proportional bar is one of the simplest possible custom-paint-free layouts (a `Stack` with two `DecoratedBox`es). Constitution Principle I: a new dependency needs a concrete need existing tools can't satisfy; this doesn't clear that bar.

**Alternatives considered**: `fl_chart`, `charts_flutter`, or a `CustomPainter`-based bar chart were considered — rejected as clear over-engineering for six static proportional bars with no interactivity, animation, or multi-series requirement; the added dependency (`fl_chart`) or the added complexity (`CustomPainter`, its own `RenderBox`/`paint` lifecycle) buys nothing the plain-widget approach doesn't already give for free, and would be the first charting dependency in a codebase that has deliberately avoided them so far (`dataviz`-style guidance notwithstanding — this is a fixed, non-interactive, six-bar display, not a dashboard).

## Decision 2 — Common scale: a fixed reference maximum, shared across every Pokémon

**Context**: spec.md FR-003 requires bar length "proportional... within a common scale shared by the six bars," and the Assumptions note bars should be "comparable between different Pokémon, not only within the same one." Official base stats range from as low as 1 (a few gimmick stats, e.g. Shedinja's HP) up to 255 (Blissey's HP is the franchise's highest single base stat as of this app's supported generations).

**Decision**: Use a single fixed reference maximum — **255** — as the denominator for every bar's `widthFactor` (`value.clamp(0, 255) / 255`), for every stat, for every Pokémon, every time. This makes two bars comparable within one Pokémon (FR-003) *and* across different Pokémon (Assumptions) without recomputing a per-render maximum, and never needs special-casing an unusually high or low value (Edge Cases) — a value at or above 255 simply fills the track, a value of 0 or 1 renders a sliver still wide enough to read as present.

**Rationale**: 255 is the actual, well-known ceiling for a single base stat across the generations this app's game catalog covers — using the real domain ceiling (not an arbitrary round number, and not a per-render `max(...)` that would make the *same* Pokémon's bars shift proportions depending on which other Pokémon happened to be compared) is both simplest to implement and matches how official in-franchise stat displays (e.g. Pokémon HOME, the games' own summary screens) already present base stats.

**Alternatives considered**: Scaling to the maximum of the *current* Pokémon's own six stats was considered — rejected because it breaks cross-Pokémon comparability (the Assumption this spec explicitly calls for): a Level-1-everything joke stat line would render with a "full" bar just like Blissey's HP, which is the opposite of informative. A configurable/theme-driven scale was also considered and rejected as unneeded configurability (Principle I) for a fixed, well-known domain ceiling.

## Decision 3 — Removing batched Pokédex loading: amend `load()`/`_fetchAndApplyView`, delete the now-dead trigger machinery

**Context**: `TeamBuilderCubit` already fetches the *entire* Pokédex index up front (`fetchPokedexIndex`, unbatched since `007-configurador-equipo-mejoras`'s research.md Decision 3) — what's batched today is only the per-species *detail* resolution: `load()`/`_fetchAndApplyView` resolve `index.take(_batchSize)` (20) plus roster occupants; `loadMoreIfNeeded`/`_resolveNextBatch` resolve 20 more at a time, triggered either by a scroll notification within 400px of the bottom (`team_builder_page.dart`, `team_builder_two_pane_layout.dart`) or by build-proximity to the end of the rendered grid (`PokedexGridSliver.onLoadMore`, added in `008-configurador-equipo-correcciones` specifically to make the *previous* batching design more reliable).

**Decision**: In `load()` and `_fetchAndApplyView`, resolve `_getPokedexDetails` for the **whole** `index` (not `index.take(_batchSize)`) in the same single call each method already makes — the roster-occupant union becomes redundant (every roster id is already part of the full index being resolved) and is dropped. Once every entry that will ever need resolving is resolved by the time `status` becomes `loaded` (or `isRefreshingPokedex` clears), `loadMoreIfNeeded`, `_resolveNextBatch`, `TeamBuilderState.isLoadingMore`, `PokedexGridSliver.onLoadMore`/`_loadMoreLookahead`, and the two `NotificationListener<ScrollNotification>` blocks have nothing left to ever trigger — they are deleted, not left as unreachable code. `updateSearch` keeps narrowing `filter` but drops its `_resolveNextBatch` call (nothing to resolve — every entry the search could ever match is already resolved).

**Rationale**: This is the minimal, same-shaped change that satisfies FR-005/FR-006 (spec.md) — the two places that already do "fetch details for some ids" just fetch details for *all* ids instead of a slice of them, using the exact same use case (`GetPokedexDetails`) and the exact same parallel-`Future.wait` repository implementation (unchanged since `004-pokedex-team-builder`) that already resolves a batch's ids concurrently. No new loading path, no new state shape for "how much is loaded" (the binary `status`/`isRefreshingPokedex` this Cubit already has is sufficient for FR-007's loading indicator — a fully-loaded-or-not Pokédex has no meaningful "70% loaded" state worth surfacing). Deleting the now-unreachable batch-trigger code (rather than leaving it inert) follows directly from Constitution Principle I.

**Alternatives considered**: Keeping the batch/trigger machinery in place but simply setting `_batchSize` to a very large number (e.g. 10000, so the "first batch" always covers everything) was considered — rejected: it leaves an entire subsystem (`loadMoreIfNeeded`, two scroll listeners, a build-proximity sliver trigger, an `isLoadingMore` flag) permanently unreachable while still compiling, reviewing, and being maintained as if it mattered, which is a worse outcome than deleting it under Principle I's "unjustified complexity must be removed" rule — the code would exist for a case (partial resolution) the product has just explicitly ruled out. Fetching every id in one `Future.wait` was also compared against fetching in fixed-size *sequential* chunks (to bound simultaneous in-flight requests) — rejected as unneeded complexity: the repository already fires one request per id concurrently for a 20-id batch today, and nothing in this feature's scope (or the constitution's performance guidance) calls for capping concurrency; if a future feature needs that, it belongs in the repository/adapter, not reintroduced as Cubit-level batching.

## Decision 4 — Loading indicator during full-index resolution

**Context**: FR-007 requires a clear loading indication while the (now potentially longer) full-index resolution is in flight, and Edge Cases call for a clean retry on failure and safe cancellation-on-supersession when the game/view changes mid-load.

**Decision**: Reuse the existing indicators unchanged — `TeamBuilderStatus.loading` (full-screen spinner, `TeamBuilderPage`'s existing `switch`) for `load()`, and `TeamBuilderState.isRefreshingPokedex` (the existing scoped `LinearProgressIndicator` in `pokedex_pane_slivers.dart`) for `_fetchAndApplyView`'s National Dex/DLC toggles. Both already exist and already satisfy "clear loading indication" and "retry on `PokedexUnavailable`" (`TeamBuilderStatus.error` plus the existing retry button) and "discard a superseded in-flight load" (`if (state.view != requestedView) return;`, already present in both methods, unchanged by this feature) — FR-007/FR-008/Edge Cases are already met by code this feature doesn't need to touch.

**Rationale**: Nothing about "resolving more ids per call" changes *when* loading starts or ends, or what "superseded" means — only how many ids get resolved within the same already-guarded call. Reusing the existing indicators is the smallest change and keeps the loading-state contract (`TeamBuilderStatus`/`isRefreshingPokedex`) exactly as `005-selector-pokedex-fixes`/`007-configurador-equipo-mejoras` already documented it.

**Alternatives considered**: A dedicated progress indicator (e.g. "342 / 903 loaded") was considered — rejected per Decision 3's rationale: with no partial-resolution state left to report (a load either hasn't finished or has, nothing in between is ever shown to the user), a percentage/counter would have to be synthesized from data the Cubit doesn't track and doesn't need to, for a mid-state the UI never actually displays.
