# Research: Layout Mitad y Mitad, Íconos de Tipo, Colores de Estadísticas y Tabla de Debilidades

## Decision 1 — Exact 50/50 split: two `Expanded(flex: 1)` panes, not a bounded-fraction width

**Context**: `TeamBuilderTwoPaneLayout` (`007-configurador-equipo-mejoras`, amended by `008-configurador-equipo-correcciones`'s research.md Decision 1) currently sizes the slots column via `(constraints.maxWidth * 0.3).clamp(280, 420)` — a width that grows toward 30% of the available space, bounded between 280 and 420px. At any width where the 30%-of-available figure lands below 420 (i.e. most desktop windows, since 420/0.3 = 1400px), the slots column is visibly narrower than the Pokédex column, matching the report ("el panel de equipo se ve muy pequeño").

**Decision**: Replace the computed/clamped width with two `Expanded` children of equal `flex` (`flex: 1` each) inside the same `Row`, separated by the existing `VerticalDivider`. Both panes now always split the available width exactly in half, regardless of window size, satisfying FR-001/FR-002 exactly. `TeamSlotRow`'s `shrinkWrap: false` (008-configurador-equipo-correcciones) is unaffected — it already fills whatever height/width its ancestor gives it.

**Rationale**: This is strictly simpler than what it replaces — no `LayoutBuilder`, no clamp, no two magic-number bounds to justify or keep in sync with anything. `Expanded(flex: 1)` is the standard Flutter idiom for "split remaining space evenly," and removes the exact code (`_minSlotsColumnWidth`/`_maxSlotsColumnWidth`/`_slotsColumnWidthFraction`) whose entire purpose was approximating a comfortable-but-bounded width — the ask now is an *exact* half, which a flex split gives for free.

**Alternatives considered**: Keeping the bounded-fraction approach but raising the fraction to 0.5 was considered — rejected: the upper bound (420px) would still cap the slots column below half on any window wider than 840px, which is most desktop windows, failing FR-001 exactly the same way the current design does. A `MediaQuery`-based breakpoint-specific fixed pair of widths was also considered and rejected as more state to maintain for no benefit over a plain 50/50 flex split.

## Decision 2 — Type icons: drop the label, size the icon to fill its box, keep an accessible name

**Context**: `PokemonTypeIcon` (`008-configurador-equipo-correcciones`) already accepts an explicit `size` — the "too small" report is about how each of the three call sites uses it, not the widget itself:
- `TeamSlot`: `PokemonTypeIcon(type: type, size: 12)` (and `size: 10` for the Tera badge) — a small fixed size chosen when this icon was a secondary detail below the sprite.
- `PokemonCustomizationCard`'s type row: wraps `PokemonTypeIcon(type: type, size: 18)` inside a Material `Chip(avatar: ..., label: Text(type.label))` — `Chip` itself adds internal padding around both the avatar and the label, so the icon is both small *and* padded.
- `PokedexTypeFilter`'s `_TypeTile`: `PokemonTypeIcon(type: type, size: 18, color: Colors.white)` next to `Text(type.label)`, inside a `Container` with `padding: EdgeInsets.symmetric(horizontal: 16, vertical: 12)` sized to fit both.

**Decision**: At each of the three call sites, remove the `Text(type.label)`/`Chip` label and let a plain, larger `SizedBox`/`Container` — sized to the space that surface already has available (the `Wrap` slot in `TeamSlot`, a fixed larger square in the customization card's type row, the existing ≥44dp touch-target box in `_TypeTile`) — hold nothing but the `PokemonTypeIcon` sized to fill it exactly, with zero internal padding between the icon and that box's edge:
- `TeamSlot`: type icons grow from `size: 12`/`10` to a size proportional to the slot's own (now-larger, per User Story 1's 50/50 split) footprint — a fixed, larger constant (`20`) replaces the old `12`, still comfortably inside the existing `Wrap`.
- `PokemonCustomizationCard`: the type row becomes a `Wrap` of plain sized boxes (e.g. `36×36`) each containing only `PokemonTypeIcon(type: type, size: 36)` — no `Chip`, no label, no chip-internal padding.
- `PokedexTypeFilter._TypeTile`: drops `Text(type.label)` and the `SizedBox(width: 6)` between icon and label; the `Container`'s `padding` shrinks to zero (the `BoxConstraints(minHeight: 48, minWidth: 64)` touch-target minimum stays, satisfying the existing `002-material-design-ui` accessibility requirement — the icon itself grows to fill that minimum box, e.g. `size: 40` inside the 48×64 minimum, rather than sitting inside 16/12px of padding).

The existing `Semantics(label: type.label)` wrapper around `_TypeTile` (already present, unchanged) satisfies FR-005 — the type stays identifiable to assistive technology even with no visible text.

**Rationale**: "No label, icon fills the container, no padding" is the report's literal ask at all three sites — removing the `Chip`/`Text`/padding is the direct, smallest change; keeping (not adding) the already-existing `Semantics` label is the smallest way to preserve FR-005 without inventing a new accessibility mechanism.

**Alternatives considered**: Keeping the label but shrinking its font size instead of removing it was considered — rejected as contrary to the explicit ask ("sin texto"). A tooltip-on-hover for the icon (in addition to `Semantics`) was considered for `_TypeTile` — rejected as unneeded for this scope: `Semantics` already covers FR-005's accessibility requirement, and this app has no other precedent of hover-tooltips on touch-target tiles (would be inconsistent with `TeamSlot`'s own type icons, which have never had one).

## Decision 3 — Stat bar color: a continuous red→yellow→green gradient over a fixed value range

**Context**: `_StatBarRow` (`009-stats-chart-full-pokedex`) currently fills every bar with the same `theme.colorScheme.primary`, regardless of value — the report asks for the color itself to signal "how good" a stat is, referencing how community reference tools (e.g. Serebii/Bulbapedia-style base-stat tables) commonly color-code base stats from red (low) through yellow/orange (mid) to green/cyan (high).

**Decision**: Add a pure function, `Color statBarColor(int value)`, local to `pokemon_customization_card.dart` (no new file — this is presentation-only styling data, not a domain concept): clamp `value` to a fixed `[_lowReference, _highReference]` range (`0` to `150` — `0` as the absolute floor, `150` as a "clearly strong" ceiling above the franchise's average base stat of roughly 70–100, chosen so the gradient's high end is reached by genuinely strong stats without needing every stat to hit the franchise's rare 255 maximum to look "good"), then interpolate through three fixed color stops — red at the low end, amber/yellow at the midpoint, a green/teal at the high end — via two `Color.lerp` calls (low→mid for the bottom half of the range, mid→high for the top half). Applied to the bar's fill color in `_StatBarRow`; the track color is unchanged (still `theme.colorScheme.surfaceContainerHighest`).

**Rationale**: A pure function of one integer is the simplest possible implementation satisfying FR-006/FR-007 — deterministic (Edge Case: "same value, same color, always" holds trivially), no state, recalculates for free every time `_StatBarRow` rebuilds with a new value (already the existing rebuild trigger from `008`'s reactive-card fix and `009`'s form-change re-render — no new listener needed). A continuous gradient (rather than a small number of hard-edged range buckets) avoids needing to justify or test exact bucket boundaries while still satisfying "low is red / mid is yellow-orange / high is green-cyan" (FR-006's own wording already describes a gradient, not fixed buckets).

**Alternatives considered**: A discrete 4–5 bucket scheme (e.g. `<60` red, `60–89` orange, `90–119` yellow, `120+` green) was considered — rejected as needing more boundary values to choose and justify than a continuous interpolation, for a visual effect the spec itself already describes as gradual ("hacia amarillo/naranja"), not stepped. Deriving the color range from the *current Pokémon's own* min/max stat (instead of a fixed franchise-wide reference range) was also considered — rejected for the same reason `009`'s Decision 2 rejected a per-Pokémon-relative bar-length scale: it would make the same numeric stat value render a different color depending on what else that Pokémon happens to have, breaking comparability across Pokémon.

## Decision 4 — Type-effectiveness chart: static domain data, authored as "only the non-neutral relationships"

**Context**: No type-effectiveness/weakness data exists anywhere in this codebase today. The 18-type matchup table has been stable across every generation this app's game catalog spans once Fairy was introduced (Generation VI) — it is franchise-constant data, not something any per-game or per-Pokémon API call could vary, and PokeAPI's own `type` resource *does* expose a `damage_relations` field per type that could be fetched — but doing so would mean an HTTP round-trip (with its own loading/failure states to design for) for data that never changes and this app already has zero existing infrastructure to cache indefinitely.

**Decision**: Author the chart as `lib/domain/team_builder/value_objects/type_effectiveness_chart.dart` — a `const Map<String, Map<String, double>>` keyed by attacking type id, each inner map listing only that attacking type's *non-neutral* (`≠ 1.0`) relationships against defending types (roughly 3–9 entries per attacking type, not all 18) — plus a pure function:

```dart
Map<String, double> typeEffectivenessAgainst(List<PokemonType> defendingTypes)
```

returning, for every one of the 18 attacking type ids, the combined multiplier a Pokémon with `defendingTypes` (1 or 2 types) receives from that attacking type — multiplying each attacking type's relationship to each of the Pokémon's own types (default `1.0` when a pair has no chart entry, i.e. is neutral), per the official combination rule (an immunity from either of the Pokémon's types makes the combined result `0`, since anything multiplied by `0` is `0`).

**Rationale**: Authoring only the non-neutral entries (compact, ~130 total entries across 18 attacking types instead of a naive 324-cell matrix) keeps the data reviewable by a human checking it against the official chart, satisfying Constitution Principle I ("unjustified complexity... must be removed" — a fully-dense matrix would be mostly `1.0`-valued noise). No network call at all avoids inventing a loading/failure/caching design for data that is, for this app's purposes, a compile-time constant — consistent with how `pokemon_stats.dart`/`pokemon_type.dart` already model other small, stable value objects as plain Dart data structures, just with the *values* sourced from PokeAPI at runtime instead of hardcoded; this one data set has no per-Pokémon variance to fetch at all.

**Alternatives considered**: Fetching each type's `damage_relations` from PokeAPI (mirroring how every other piece of Pokédex data in this app is sourced) was considered — rejected: it would need 18 additional HTTP requests (one per type) merged client-side into the same shape this decision already produces locally, for data that literally cannot differ between requests within this app's supported generation range, adding real network/failure-handling surface for zero behavioral benefit. Computing effectiveness lazily by scanning a flat list of `(attackingType, defendingType, multiplier)` triples instead of a nested map was also considered — rejected as a slower, harder-to-author shape for the same information a nested map already expresses directly.
